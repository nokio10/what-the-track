## Дополнение по ошибкам `RemoteDisconnected` при скачивании из Яндекса

После следующего пользовательского прогона в логах регулярно появлялись предупреждения вида:

- `LRC ... RemoteDisconnected('Remote end closed connection without response')`
- `Метаданные ... RemoteDisconnected(...)`

Разбор показал следующее:

1. Это не новый тип ошибки от дедупликации ссылок. Дедупликация только уменьшает количество треков в очереди и не добавляет новые HTTP-запросы.
2. Эти предупреждения уже генерировались существующей retry-логикой `download / metadata / lyrics / supplement`, просто теперь пользователь обратил на них внимание в полном логе.
3. При этом сам пайплайн действительно делал слишком плотную пачку запросов к API Яндекса на один трек:
   - `client.tracks([tid])` перед скачиванием;
   - повторный `client.tracks([tid])` для метаданных;
   - `track_info.get_lyrics('LRC')`;
   - `lyrics_obj.fetch_lyrics()`;
   - `track_info.get_supplement()` как fallback.

Что было добавлено:

- новый модуль `yandex_request_logic.py` с `YandexRequestThrottle`, который ограничивает частоту запросов к API Яндекса;
- в `generator_service.py` перед вызовами `tracks(...)`, `get_lyrics(...)`, `fetch_lyrics()` и `get_supplement()` теперь ставится throttle-пауза;
- если `track_info` уже получен на этапе скачивания, он повторно используется для метаданных, чтобы не делать лишний второй `client.tracks([tid])` без необходимости;
- добавлены TDD-сценарии в `tests/test_yandex_request_logic.py` на базовое поведение throttling:
  - первый запрос без задержки;
  - второй мгновенный запрос с ожиданием минимального интервала;
  - следующий запрос после паузы без дополнительного sleep.

После повторного пользовательского прогона стало видно, что базовый интервал `0.45s` снизил часть сбоев, но не устранил их полностью: отдельные `RemoteDisconnected` и `Timed out` всё ещё оставались на скачивании, LRC и supplement.

Что усилено после этого:

- базовый интервал Yandex throttle поднят с `0.45s` до `0.85s`;
- после сетевой ошибки throttle получает дополнительный failure cooldown `1.5s`, чтобы следующая попытка не возвращалась к API слишком быстро;
- `YandexRequestThrottle` расширен методом `penalize(...)`;
- в `tests/test_yandex_request_logic.py` добавлен TDD-сценарий на штрафную паузу после ошибки.

## Дополнение по двухстрочному тексту вопроса в `LYRICS_ALGO`

После отдельного пользовательского прогона выяснилось, что двухстрочный вопрос появлялся не во всех `LYRICS_ALGO` кейсах. Пример: строка с ответом `Которым теперь плевать на любые новости` показывалась без предыдущей строки `И вот у Веры химеры и робот-пылесос`.

Разбор показал причину:

- логика двухстрочного контекста пыталась поднять предыдущую строку через `lyrics_line_idx` / `lyrics_line` в `all_words`;
- если word-level remap не проставлял соседнюю строку достаточно хорошо, `build_context_string(...)` видел только текущую answer line и возвращал одну строку.

Что исправлено:

- `select_word_from_lyrics_algorithmically(...)` теперь возвращает не только `answer_line`, но и `answer_line_idx`;
- `rank_lyrics_candidates(...)` сохраняет `line_idx` в candidate payload;
- `build_context_string(...)` получил fallback на предыдущую строку напрямую из official lyrics по `answer_line_idx`, а не только через `all_words`;
- добавлены TDD-сценарии в `tests/test_question_logic.py`:
  - на возврат `answer_line_idx` из lyrics selector;
  - на двухстрочный контекст даже при отсутствии хорошей разметки предыдущей строки в `all_words`.

После следующей проверки выяснилось, что этого всё ещё недостаточно для общего режима: некоторые вопросы без хорошей lyrics-line разметки по-прежнему отображались в одну строку, хотя в распознанном тексте уже было две естественные фразы. Примеры:

- `Позвони еще разок, ты ___`
- `Не грусти. Всё ___`

Что было доработано:

- общий путь `build_context_string(...)` теперь собирает контекст по фразовым блокам, а не только в один плоский список токенов;
- перенос строки в general mode ставится по естественной границе: `is_eol` предыдущего слова или заметной паузе между словами;
- если найдено несколько фразовых блоков, в вопрос выводятся последние две строки;
- добавлены TDD-сценарии в `tests/test_question_logic.py` на:
  - `Потерялось, не нашлось\nПозвони еще разок, ты ___`
  - `Не грусти.\nВсё ___`

## Offline Web UI Note

During an additional review I found a separate offline-start issue in the web UI.

### Root cause

The browser pages depended on external CDNs for critical runtime assets:

- `templates/index.html` loaded Socket.IO client from Cloudflare CDN;
- `templates/admin.html` loaded Socket.IO client from Cloudflare CDN;
- `templates/admin.html` also depended on Bootstrap bundle from jsDelivr for modal behavior.

When the host/container had no internet access, the HTML could still be served by local Nginx, but the frontend runtime could fail before initialization because `io()` was unavailable, and admin modals could stop working because `bootstrap.Modal` was missing.

This is separate from Docker port publishing:

- external browser entrypoint is still Nginx on host port `5002`;
- `game-app` is only exposed internally to Compose and is not published directly.

### First attempted fix and correction

An intermediate attempt switched templates to `/socket.io/socket.io.js`, but this path was incorrect for the current Flask-SocketIO setup.

In this project:

- `/socket.io` is the realtime transport endpoint proxied by Nginx;
- it is not a guaranteed static source of the browser client script;
- therefore the browser still failed with "client did not load".

### Final fix

- both templates now use local `static/socketio-lite.js`;
- `socketio-lite.js` is a lightweight in-repo realtime client that implements the subset of Engine.IO v4 / Socket.IO v4 behavior used by this game:
  - default namespace connect;
  - JSON event receive/send;
  - ping/pong handling;
  - reconnect handling;
  - `socket.id`;
- both templates now include local `static/offline-fallback.css` instead of relying on Bootstrap / Font Awesome / Google Fonts;
- admin page now has a lightweight modal shim compatible with existing `bootstrap.Modal` calls, so settings and saved-games dialogs still open without Bootstrap bundle;
- both pages now show a visible diagnostic banner if the local realtime client script did not load, instead of silently dying in browser JS.

### Added TDD coverage

Added `tests/test_web_templates.py` with regression checks for:

- local realtime client usage in both templates;
- presence of local offline stylesheet;
- absence of Bootstrap bundle dependency in admin template;
- presence of the local modal fallback shim;
- existence of local `static/socketio-lite.js`.

### Important residual note

These fixes address the "no internet, but containers are up" case.

If the container is started with networking fully disabled (for example `--network none`), then this is a different class of problem:

- published host ports may not behave as expected;
- Nginx may lose access to `game-app`;
- `/socket.io` proxying can fail even with correct frontend files.

In that scenario the correct fix is to keep Docker networking enabled and block only external egress, not remove container networking entirely.

### Follow-up correction for remote stability

After manual verification it became clear that using only local `socketio-lite.js` solved offline startup, but it also reduced transport flexibility for remote users because the lightweight client is WebSocket-only.

That matters for external access through KeenDNS / reverse proxy chains, where the full Socket.IO browser client is generally more resilient thanks to mature reconnect and transport handling.

So the frontend was adjusted again:

- primary client path: external Socket.IO browser client `4.0.1` from CDN;
- fallback path on load failure: local `static/socketio-lite.js`.

Result:

- offline local startup still works because browser falls back to the local script;
- remote access keeps the more battle-tested Socket.IO client whenever CDN access is available.

### Follow-up visual fix for admin/player UI

After switching to offline-safe assets only, the UI lost part of the original Bootstrap-based look:

- some border radiuses looked flatter;
- spacing and component defaults drifted from the original design;
- admin modal visually shifted.

To restore the original appearance without losing offline support:

- Bootstrap CSS was added back as the primary visual source;
- Bootstrap bundle was added back for admin page behavior;
- Font Awesome and Google Fonts were added back as primary visual assets;
- local `offline-fallback.css` stays in place as the offline backup layer.

This means:

- online / remote users see the original interface much closer to the old version;
- offline local users still get a functional UI instead of a broken page.

### Follow-up fix for repeated context duplication

Another manual regression showed that `build_context_string(...)` could still duplicate almost the entire phrase when `target_word["skipped_before"]` contained a long repeated block and the actual overlap started in the middle of that block, not at its prefix.

What was wrong:

- old overlap suppression only handled `context_suffix == skipped_prefix`;
- but in real data the skipped block for the answer word could look like:
  - repeated phrase from the start of the line;
  - then the already visible suffix of the current context;
  - then just one or two truly missing final words.

What was changed:

- overlap merge in `question_logic.py` now:
  - first ignores `extra_tokens` that are already fully contained in the current context;
  - then searches for the longest suffix of current context appearing anywhere inside `extra_tokens`, not only at position `0`;
  - appends only the truly missing tail after that match.

Added regression coverage for the exact `...жди пару секунд...слушай не ___` shape in `tests/test_question_logic.py`.

### Final correction for lyrics-mode context building

One more manual run showed that overlap suppression alone was still insufficient for some lyrics tracks.

The deeper issue was:

- `generator_service.py` already passed `is_lyrics_mode=True` and the official `answer_line`;
- but `question_logic.build_context_string(...)` ignored these kwargs and still reconstructed text from word-level `skipped_before`;
- therefore any noisy alignment artifacts in `skipped_before` could still leak into the visible question text.

Final fix:

- in lyrics mode, `build_context_string(...)` now first tries to build the visible prompt directly from official `answer_line`;
- it finds the answer word inside that line and returns the clean prefix before it;
- only if this fails does it fall back to the old word-level context assembly.

This makes lyrics-mode questions deterministic and much less sensitive to Whisper/alignment noise in the textual prompt.

### Follow-up tuning for answer guard and visible context size

Two UX adjustments were requested after manual testing:

1. increase the pre-answer audio guard from `75ms` to `100ms`, because elongated word onsets could still leak into the question audio;
2. increase visible lyrics-mode context back toward roughly two lines, because the previous clean `answer_line` fix made prompts shorter than desired.

What was changed:

- `QUESTION_WORD_GUARD_MS` in `question_logic.py` was increased from `75` to `100`;
- lyrics-mode `build_context_string(...)` now prepends the previous mapped official lyrics line when available;
- player UI question text now uses `white-space: pre-line`, so the inserted line break is actually rendered as two lines in browser.

Added TDD coverage for:

- `100ms` pre-answer guard;
- two-line lyrics-mode context rendering.

## Follow-up fix for duplicate Yandex track links

Another practical issue appeared before the download stage: sometimes the incoming list contained the same Yandex track link multiple times.

Required behavior:

- remove duplicates before downloading;
- compare duplicates by Yandex track identity, not by raw full URL string;
- for direct track links, use:
  - `album/<album_id>/track/<track_id>` when album is present;
  - `track/<track_id>` for bare track links.

What was added:

- new pure helper module `yandex_url_logic.py`;
- `extract_yandex_track_identity(url)` parses:
  - `album/.../track/...`
  - `track/...`
- `dedupe_yandex_track_urls(urls)` preserves input order, keeps the first occurrence, and returns duplicate refs for logging.

Integration:

- `generator_service.py` now dedupes input URLs before the Yandex download loop starts;
- duplicates are logged explicitly, so it is visible in generation logs what was filtered out.

Added TDD coverage in `tests/test_yandex_url_logic.py` for:

- extracting `album/<album_id>/track/<track_id>`;
- deduping same track with different query params;
- preserving same track id from different albums;
- deduping bare `track/<track_id>` links;
- skipping blank lines.
  - сохранение односимвольных русских слов;
  - новый guard в 75 мс перед словом-ответом;
  - детерминированный algorithm-only выбор;
  - приоритет корректно привязанного к строке вхождения.

  - регрессия на сохранение пропущенных коротких слов через `skipped_before`.

## Найденные проблемы

### 1. Короткие слова отбрасывались ещё на этапе сборки `all_words`

Файл: `generator_service.py`

Причина:

- в `process_audio_with_whisperx(...)` стоял фильтр `len(clean) < 2`;
- в `forced_align_lyrics(...)` стоял такой же фильтр;
- это гарантированно выбрасывало `и`, `в`, `к`, `с`, `я`, `о`, `у`, `а` ещё до контекстной сборки.

Эффект:

- ломался текст вопроса;
- ухудшалось совмещение с official lyrics;
- пропадали предлоги перед словом-ответом.

### 2. Перед словом-ответом фактически резалось больше, чем заявленные 200 мс

Файл: `generator_service.py`

Причина:

- `calculate_timings(...)` резал по `target_start - 200ms`;
- затем экспорт вопроса делал ещё `q_times[1] - 100`;
- в сумме последнее слово перед ответом могло обрезаться примерно на 300 мс.

Эффект:

- игрок не слышал последнее слово перед словом-вопросом;
- ухудшалось восприятие рифмы и концовки фразы.

### 3. LLM всё ещё оставалась в боевом пайплайне

Файл: `generator_service.py`

Причина:

- при отсутствии lyrics использовался путь `WHISPER + LLM`;
- при провале `lyrics_algo` происходил fallback на `_select_word_llm_flow(...)`;
- в конфигах и зависимостях оставались следы LLM-пайплайна.

Эффект:

- недетерминированное поведение;
- лишняя зависимость от `ollama`;
- несовпадение между желаемой архитектурой и реальной.

### 4. Более устойчивый line-aware remap существовал, но не был подключён в генератор

Файлы:

- `lyrics_alignment_experiment.py`
- `generator_service.py`

Причина:

- в проекте уже был более качественный `remap_words_to_official_by_line(...)`;
- но генератор продолжал жить только на старом greedy `align_words_to_lyrics(...)`.

Эффект:

- хуже переносились пропущенные слова;
- хуже переживались расхождения между Whisper-строками и official lyrics.

### 5. Общий алгоритм выбора слова был не до конца детерминированным

Файл: `generator_service.py`

Причина:

- старый `get_algorithmic_choice(...)` брал `random.choice(...)` из топ-3.

Эффект:

- одно и то же аудио могло давать разные ответы между прогонами;
- сложнее воспроизводить баги и регрессии.

### 6. Конфиг и зависимости расходились с реальным поведением

Файлы:

- `requirements.txt`
- `docker-compose.yml`
- `docker-compose.nvidia.yml`

Причина:

- `ollama` всё ещё был в зависимостях;
- в compose оставались LLM-переменные, хотя целевой путь уже algorithm-only.

Эффект:

- путаница при деплое;
- ощущение, что LLM всё ещё обязательна.

## Что исправлено

### 1. Вынесена чистая testable-логика в новый модуль

Добавлен файл:

- `question_logic.py`

Туда вынесены:

- фильтрация коротких слов;
- алгоритмический scoring без LLM;
- детерминированный выбор кандидата;
- тайминги с guard в 75 мс;
- сборка текстового контекста.

Это уменьшает связность с Flask/Whisper и делает поведение пригодным для unit-тестов.

### 2. Короткие служебные слова больше не выкидываются автоматически

В `question_logic.py` добавлен `should_keep_word_token(...)`:

- разрешены частотные односимвольные русские слова: `а`, `и`, `в`, `к`, `с`, `у`, `о`, `я`;
- для них снижен минимальный порог confidence;
- остальной мусор по-прежнему режется.

`generator_service.py` переведён на этот фильтр в:

- `process_audio_with_whisperx(...)`
- `forced_align_lyrics(...)`

### 3. Question cut переведён на 75 мс

Новая константа:

- `QUESTION_WORD_GUARD_MS = 75`

Что изменено:

- алгоритм расчёта вопроса теперь режет по `target_start - 75ms`;
- экспорт вопроса больше не делает дополнительный `-100ms` на конце;
- вспомогательная LRC-логика тоже приведена к тому же guard.

### 4. Боевой выбор слова переведён на algorithm-only

Теперь:

- при наличии lyrics используется `qlogic.select_word_from_lyrics_algorithmically(...)`;
- при провале lyrics-режима идёт fallback только на deterministic algo;
- без lyrics используется только `WHISPER + ALGO`.

Дополнительно:

- `_select_word_llm_flow(...)` оставлен только как совместимый shim и тоже возвращает algo;
- `correct_transcription_with_llm(...)` и `get_quiz_data_llm(...)` безопасно деградируют, если `ollama` не установлена.

### 5. Подключён line-aware remap после первичного alignment

Теперь в lyrics-режиме:

1. идёт базовый `align_words_to_lyrics(...)`;
2. затем поверх него запускается `remap_words_to_official_by_line(...)`;
3. при успешном remap генератор использует улучшенный результат.

Это особенно важно для кейсов, где:

- Whisper пропустил короткие слова;
- строка распалась не так, как в official lyrics;
- нужно донести пропущенные слова через `skipped_before`.

### 6. Общий selector сделан детерминированным

В `question_logic.py`:

- убран `random.choice(...)`;
- выбор идёт по максимуму score;
- добавлены штрафы за повторы рядом с ответом и повторяющиеся строки;
- добавлены бонусы за более позднее, но ещё безопасное положение ответа в треке.

### 7. Убраны лишние боевые зависимости и конфиг-шум

Изменения:

- из `docker-compose.yml` удалены `OLLAMA_HOST` и `ENABLE_LLM_SELECTOR`;
- из `docker-compose.nvidia.yml` удалён `ENABLE_LLM_SELECTOR`.

## Дополнение после ручного прогона

После первого раунда пользовательский прогон выявил ещё 3 практических проблемы:

1. Иногда вопросовое окно начиналось длинным проигрышем, а полезный текст вступал слишком поздно.
2. В lyrics-режиме `skipped_before` учитывался только у слова-ответа, но не у промежуточных слов контекста.
3. В no-lyrics режиме короткий предлог мог присутствовать в segment text, но теряться на word-level alignment и не попадать в текст вопроса.

Что дополнительно исправлено:

- в `question_logic.py` добавлена проверка `question_window_has_enough_context(...)`, которая отклоняет кандидатов с длинным инструментальным вступлением перед текстом;
- `build_context_string(...)` теперь восстанавливает `skipped_before` по всей цепочке контекстных слов, а не только прямо перед ответом;
- добавлен `recover_segment_skipped_tokens(...)`, который подтягивает короткие служебные слова из `segment["text"]` обратно к ближайшему следующему word-token;
- в `generation_task(...)` retry для lyrics-треков теперь идёт по ранжированному списку lyrics-кандидатов, а не сразу по общему fallback scoring.

После следующего пользовательского прогона обнаружился ещё один класс проблем:

1. иногда терялось короткое, но смысловое слово вроде `весь`, хотя оно было важно для контекста;
2. при сборке `context` некоторые `skipped_before` перекрывались с уже набранным хвостом и создавали дубли фраз.

Что было добавлено после этого:

- `recover_segment_skipped_tokens(...)` расширен так, чтобы сохранять не только предлоги, но и короткие смысловые слова длиной до 5 букв, если они выглядят валидными;
- `build_context_string(...)` переведён на overlap-aware merge, чтобы `skipped_before` не дублировал уже собранные токены;
- добавлены TDD-сценарии на:
  - восстановление слова `весь`;
  - suppression overlap-дубликатов в контексте.

Под это добавлены новые TDD-сценарии в:

- `tests/test_question_logic.py`
